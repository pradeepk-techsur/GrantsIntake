<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | Applicant browser fetching notification records from GET /api/v1/notifications |
| db→render | Notification title/body (originally written by the server on disposition) reflected back to the applicant's browser |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02-01 | Information disclosure | GET /notifications handler (src/routes/intakeQueue.ts) | mitigate | Server derives `user_id` from JWT (`req.user.user_id`) — never from query params. `intakeQueueService.getNotifications` filters `WHERE recipient_user_id = $1` using that server-derived value. IDOR: one user cannot read another's notifications. Already implemented in 06-01; this plan adds no new backend code. |
| T-06-02-02 | Information disclosure | NotificationsPage.tsx — renders notification body | mitigate | Notification `title` and `body` fields are set server-side by `createNotification` in `intakeQueueService` using fixed template strings (not user-supplied content). React's JSX string interpolation `{notification.body}` HTML-escapes output — no XSS risk for text nodes. |
| T-06-02-03 | Elevation of privilege | NotificationsPage route — applicant-only | mitigate | Route lives inside `<Route path="/applicant" element={<ApplicantLayout />}>`. `ApplicantLayout` enforces auth guard (redirects to /login if no access token in Zustand store) — same guard as all other applicant pages. No additional work needed. |
| T-06-02-04 | Tampering | PUT /notifications/:id/read — IDOR | accept | Backend already implemented in 06-01: `markNotificationRead` checks `WHERE notification_id=$1 AND recipient_user_id=$2` using server-derived user_id. This plan adds no backend code; the guard is inherited. Residual risk: none beyond what was accepted in 06-01. |
</threat_model>
