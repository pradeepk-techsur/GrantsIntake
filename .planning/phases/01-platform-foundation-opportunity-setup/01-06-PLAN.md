<objective>
Fix the silent "Create Opportunity" failure that blocks the Opportunity Builder from being reached.

**Root cause (diagnosed in UAT Test 3):** `TemplateLibrary.tsx` sends `funding_amount_max: 0` in the POST body, but `createOpportunitySchema` in `src/routes/opportunities.ts` requires `z.number().positive()` (> 0). The API returns a `VALIDATION_ERROR` which is swallowed by a bare `catch {}` block — so the user clicks "Create Opportunity" and nothing happens. Navigation to the Opportunity Builder never fires.

**The fix has two parts:**
1. Make `funding_amount_max` optional in `createOpportunitySchema` (consistent with `updateOpportunitySchema` which already has `.optional()`). Filling in the amount is a builder task, not a creation prerequisite.
2. Remove `funding_amount_max: 0` from the TemplateLibrary create payload, and replace the silent `catch {}` with an error-surfacing block that shows a USWDS error alert to the user.

Purpose: Unblocks UAT Test 3 (Create Opportunity from template) and transitively unblocks UAT Tests 4–7 (all skipped because the Opportunity Builder was unreachable).
Output: A working template-selection → Opportunity Builder navigation flow, with visible error feedback if creation fails for any other reason.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | React TemplateLibrary POSTs CreateOpportunityPayload into POST /api/v1/programs/:id/opportunities handler |
| db→render | API error messages from the server (e.g. "VALIDATION_ERROR") cross into the client and are rendered in the error alert |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06-01 | Tampering | `createOpportunitySchema` in `src/routes/opportunities.ts` | mitigate | Making `funding_amount_max` optional does not weaken the positive-number constraint — when present it is still validated by `z.number().positive()`. The Zod parse on line ~29 of `opportunities.ts` enforces the constraint on any supplied value. Omitting the field simply skips the check, which is the intended UX: fill it in the builder. No user-controlled relaxation of other constraints. |
| T-01-06-02 | Information disclosure | `catch (err) → createError state → USWDS alert render` in `TemplateLibrary.tsx` | accept | Error messages rendered to the user originate from structured API responses (`{"error":"VALIDATION_ERROR","message":"..."}`) or a generic client fallback string. No stack traces, internal file paths, DB query details, or other sensitive internals are propagated. The route is authenticated (grantor_admin role required) — unauthenticated users cannot reach the modal. Residual risk: API error messages may hint at internal field names (e.g. "must be positive"); accepted because field names are not sensitive for authenticated grantors, and the disclosure is bounded to the authenticated session. |
| T-01-06-03 | Elevation of privilege | POST /api/v1/programs/:id/opportunities | mitigate | No change to IDOR or ownership guards. The existing `getGrantorOrgIdForUser()` pattern derives `grantor_org_id` server-side from the authenticated user's `grantor_roles` — never from the request body. Making `funding_amount_max` optional does not affect the org-ownership check path in `src/routes/opportunities.ts` (the IDOR guard runs before schema parse). Mitigation is in the existing `requireRole('grantor_admin')` middleware and `verifyOpportunityAccess()` helper. |
</threat_model>
