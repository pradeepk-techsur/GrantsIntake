## Summary
This is a **re-audit** of Phase 8 after plan **08-07** (import-visibility gap closure, uat/5) landed on top of the 08-06 endpoint fix. The phase-wide STRIDE register was rebuilt directly from the on-disk external-opportunity subsystem — no phase-isolated `git diff` exists (the `phase-8` branch is squashed to 3 commits: `70b77f5` gap-closure, `e20c39a` UAT re-verify, `93c9b33` execution complete). The 08-06 and 08-07 per-plan `<threat_model>` blocks were treated as narrow gap-closure registers and verified against current code, not as the phase register. **08-07 introduced one NEW authenticated read endpoint** (`GET /external-opportunities/imported`) plus a backing service query and a client imported-opportunities list. All three 08-07 threat claims (T-08-01 info-disclosure, T-08-02 SQLi, T-08-03 route-ordering/EoP) were verified and hold — and the implementation is in fact **stronger than the 08-07 plan/summary documented**: the plan claimed the imported list is "not per-applicant scoped," but the shipped query scopes strictly to the caller via `WHERE ... AND o.created_by = $3` (JWT `req.user!.user_id`), so it is an owner-scoped read with no cross-tenant leakage. The prior authorization posture holds across the phase: every authenticated endpoint derives the acting user from the JWT (never the request body); admin refresh routes remain `authenticate` + `requireRole('grantor_admin')`; all SQL is parameterized (static ORDER BY, clamped LIMIT/OFFSET); the outbound Grants.gov host is fixed. **No new HIGH/CRITICAL issue.** Prior finding **F-01 (MEDIUM, `javascript:`-scheme stored-XSS on external `href`s) remains OPEN** — re-confirmed: still no `safeHref`/scheme guard anywhere in `client/src`, and 08-07's WorkspaceListPage imported-opps list renders NO external `href` (text-only), so it introduces no new href sink. Prior **F-02 (LOW) remains an accepted risk**. Ship-able; F-01 should be hardened.

## Confirmed findings
> OPEN findings only. Each survived adversarial refutation.

### F-01: Unvalidated URL scheme on externally-sourced links (`javascript:` stored-XSS vector) — MEDIUM
- **Status:** Unchanged from prior audit — **not fixed.** Re-verified against current code including the 08-07 landing: the copy-verbatim `packageURL` path persists (`normalizePackages`), and a repo-wide grep confirms **no `safeHref`/`sanitizeUrl`/`isSafeUrl` guard exists anywhere in `client/src`**. 08-07's new imported-opps list does NOT add a new href sink (text-only), so the finding's scope is unchanged: the two href sites on the detail page.
- **Category:** xss (stored, scheme-injection)
- **Location:** client/src/pages/applicant/ExternalOpportunityDetailPage.tsx:183 (`href={opp.application_package_url}`) and :197 (`href={opp.source_url}`); untrusted origin at src/services/external/grantsGovService.ts:55 (`flat[0].packageURL` copied via `String(...)`), :70-71 (`first.packageURL` copied verbatim), surfaced through :220 (`packageUrl = pkgs.packageUrl`) and :267 (`application_package_url: packageUrl`).
- **Description:** `application_package_url` is copied verbatim from the Grants.gov detail response (`packages[0].packageURL` or `opportunityPkgs[].packageURL`) into the canonical record with **no scheme validation** — `normalizePackages` only `String(...)`-coerces the type. The value is persisted, served by the **public** `GET /external-opportunities/:id` endpoint, and rendered directly as an anchor `href` on the applicant detail page. React does not neutralize `javascript:`-scheme URLs in `href` at runtime, so a stored value like `javascript:fetch('/api/v1/...',{headers:{Authorization:...}})` would execute in the victim's session on click. `source_url` is server-constructed (`PUBLIC_DETAIL_URL`, grantsGovService.ts:20-21,:256) and therefore not attacker-influenced, but shares the same unguarded rendering path and should be guarded as defense-in-depth.
- **Exploit:** Requires the injected value to appear in the Grants.gov detail payload the ingester consumes — a malicious/compromised upstream response, a MitM on the outbound fetch, or an operator pointing `GRANTS_GOV_API_BASE` at an attacker-controlled host. Given a hostile `packageURL`, any visitor (detail is public) who opens the opportunity and clicks "Open package ↗" runs attacker script in-origin. The trusted-federal-API upstream and absence of a direct user-injection path cap this at MEDIUM, not HIGH.
- **Fix:** Validate the URL scheme before storing and/or before rendering — allow only `http:`/`https:` (reject/blank `javascript:`, `data:`, `vbscript:`). Preferred: sanitize at normalize time in `grantsGovService` (`normalizePackages`/`normalizeOpportunity`) so the persisted/public value is always safe, plus a render-time `safeHref()` guard shared by both `href` sites.
